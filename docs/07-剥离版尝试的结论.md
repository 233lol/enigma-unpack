# 05 · 剥离版与自检分析（为什么最终选择启动器）

> **说明（本项目更新）**：本文记录了早期「直接剥离壳」的探索与当时的取舍。
> 后来发现 **`WinMain` 是唯一被虚拟化的函数**，并用 HSP3 源码语义写回原生
> WinMain，从而得到可独立运行的原程序（见 [05-脱壳与重建.md](05-脱壳与重建.md)）。
> 本项目已把「独立 exe」这条路实现出来（`run_all.py` / `一键脱壳重建.bat`）；
> 启动器（`一键启动游戏.bat`）仍然是最省事的玩法。本文的价值在于记录了
> 早期失败路径、`.data` 纯净性问题与各项修复。

> 这一页解释：为什么不做一个「无壳、双击即玩」的独立 exe，
> 而是采用运行时补丁的启动器方案。

## 2. 最后的墙：Enigma 的代码虚拟化

剥离版在 CRT 初始化之后仍然无法进入游戏。决定性证据：

### 2.1 WinMain 是 VM 桩

原程序入口链路里的 `0x41AFF0`（WinMain）反汇编：

```
0x41AFF0: e8 8f fb 18 00    call 0x5AAB84
```

- `0x5AAB84` 位于壳的映像范围（原始进程 `0x453000..0xC32000`）；
- 在剥离进程里 `VirtualQueryEx(0x5AAB84)` → **MEM_RESERVE（未提交）**。

### 2.2 实跑地址落在 VM 区

调试器捕获的异常地址：

```
0x5A4204C9 = 0x5A000000 + 0x4204C9
```

这是 **Enigma 虚拟机的映射基址**；剥离进程里不存在该区域。

### 2.3 结论

**游戏主逻辑不是普通机器码**，而是壳的虚拟机入口桩；
真正的代码由壳在运行时解释执行。要脱离壳运行，必须对 Enigma 的
VM 做**完整的 devirtualization**（重写它的指令解释器与所有 handler）。

这不是补几个 API 返回值能解决的，工作量与前几轮不是一个量级，
且与「正常游玩」无关。

---

## 3. 为什么不继续做剥离

| 因素 | 说明 |
|---|---|
| 收益 | 只是「不弹注册框」；启动器已经做到 |
| 成本 | 需要逆向整个 Enigma VM（指令集、handler、加密） |
| 风险 | 极易引入新的崩溃/数据损坏 |
| 合法性 | 私钥不可得；剥离版也无法通过作者的公钥许可校验 |

因此项目**选择启动器方案**：它直接利用壳自己的「注册成功」后续流程，
不触碰被虚拟化的代码，稳定且可复现。

## 5. 启动器 vs 剥离版

| 项目 | 启动器 | 剥离版 |
|---|---|---|
| 能进游戏 | ✅ | ❌（VM 桩） |
| 需要原 `crackme.exe` | ✅ | ❌ |
| 每次启动要运行 | ✅（1 次双击） | — |
| 修改磁盘 | ❌ | — |
| 稳定性 | ✅ 多次验证 | 实验性 |

**结论：游玩请用启动器；剥离版仅作为逆向研究记录保留。**
